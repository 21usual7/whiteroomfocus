# Техническая реализуемость

> Основная платформа — Linux desktop. Среда разработчика — Omarchy (Arch + Hyprland, Wayland).
> Пометка **[проверено]** означает, что есть ссылка на документацию. **[инженерная оценка]** — знание без проверки в этом исследовании; перед реализацией подтвердить прототипом.

## 1. Главное ограничение: на Wayland нет общего API

На X11 любое приложение может узнать активное окно (`_NET_ACTIVE_WINDOW`) и следить за другими окнами. Wayland так сделать **не даёт намеренно**: это часть модели безопасности. Каждый композитор решает сам.

| Окружение | Как узнать активное окно | Как закрыть или скрыть окно | Статус |
|---|---|---|---|
| **Hyprland** | Сокет событий `$XDG_RUNTIME_DIR/hypr/<HIS>/.socket2.sock`, событие `activewindow>>CLASS,TITLE` | `hyprctl dispatch closewindow` / `movetoworkspacesilent` | **[проверено]** [wiki](https://wiki.hypr.land/IPC/) |
| **Sway и другие wlroots** | i3-совместимый IPC: подписка на `window`, или протокол `wlr-foreign-toplevel-management` | Команды IPC | [инженерная оценка]; aw-watcher-window-wayland работает на wlroots |
| **KDE Plasma (KWin)** | Только через скрипт KWin или D-Bus | Скрипт KWin | Готового протокола нет, ActivityWatch официально не поддерживает. [KDE discuss](https://discuss.kde.org/t/feature-request-implement-wayland-protocol-in-kwin-to-support-activitywatch/30499) |
| **GNOME (Mutter)** | Только через расширение GNOME Shell (пример: `focused-window-dbus`) | Через расширение | Обходной путь от пользователей. [issue](https://github.gg22.workers.dev/ActivityWatch/activitywatch/issues/1218) |
| **X11** | `_NET_ACTIVE_WINDOW`, EWMH | `xdotool`, `wmctrl` | Работает везде |

Сторонний `awatcher` заявляет поддержку Sway, Hyprland, KDE, GNOME и X11 — **[не проверено]**, утверждение видел в одном коммите документации ActivityWatch. Его стоит изучить как образец адаптеров.

**Решение.** В ядре интерфейс `ActivitySource` и отдельные адаптеры для каждого окружения. В MVP — **Hyprland + X11**. Sway, KDE и GNOME позже. Если адаптера нет, приложение работает без отслеживания окон: это штатный режим, а не ошибка.

## 2. Блокировка

Универсального способа «запретить запуск приложения» на Linux без root нет.

| Способ | Что блокирует | Нужен root | Надёжность | Оценка |
|---|---|---|---|---|
| **Расширение браузера** (Chrome MV3 `declarativeNetRequest`, Firefox `webRequest`) | Сайты | Нет | Высокая внутри браузера; обходится другим браузером | **Основной способ** |
| Закрытие или скрытие окна через IPC композитора | Окна приложений | Нет | Средняя: окно появилось, потом исчезло | Для Hyprland/Sway |
| Слежение за процессами через `/proc` + `SIGTERM` | Процессы | Нет (для своих процессов) | Средняя, есть задержка опроса, грубо | Только как опция, с предупреждением |
| `/etc/hosts` или локальный DNS | Сайты во всех приложениях | **Да** | Высокая, но DoH в браузере обходит | Опция через polkit-помощник; не в MVP |
| nftables, cgroups | Сеть, процессы | Да | Высокая | Избыточно, риск сломать систему |

**[проверено]** Native messaging в Chrome: манифест хоста в `~/.config/google-chrome/NativeMessagingHosts/` (Chromium — `~/.config/chromium/NativeMessagingHosts/`), путь абсолютный, `allowed_origins` без шаблонов. `connectNative()` держит процесс хоста живым, пока открыт порт. [Chrome docs](https://developer.chrome.com/docs/extensions/mv3/nativeMessaging)

**Решение.**
- Сайты: расширение получает список блокировки от WHITE ROOM через native messaging и применяет его через `declarativeNetRequest`.
- Приложения: «мягкая» блокировка. Окно переносится на скрытый workspace с уведомлением «это не входит в план сессии; открыть всё равно?» Пользователь решает сам, а событие попадает в журнал.
- **Аварийный выход** всегда доступен: горячая клавиша и пункт в трее. Он мгновенно снимает все ограничения. Root-способы — только позже и только по отдельному согласию.

## 3. Сигналы для мониторинга: что можно и что нельзя узнать

| Источник | Что даёт | Чего **не** даёт | Приватность |
|---|---|---|---|
| Класс и заголовок активного окна | Какое приложение, иногда файл или страница | Понимание, обучение | Заголовки могут содержать личное (почта, чаты) → хранить локально, фильтровать |
| Расширение браузера (URL активной вкладки) | Домен, относится ли он к теме | Читает ли человек, понимает ли | Хранить только домен; полный URL — по разрешению |
| Расширение IDE (VS Code, JetBrains, Neovim) | Файлы, запуски тестов, ошибки компиляции | Качество мышления | Хорошее соотношение сигнала к риску |
| Время простоя (idle) | Отошёл от компьютера | Думает или ушёл | На Wayland: протокол `ext-idle-notify`, [инженерная оценка] |
| Скриншоты + vision-модель | Содержимое экрана | Всё равно не понимание | **Высокий риск.** Только по запросу, локально, без хранения |
| Ответы на вопросы WHITE ROOM | **Что удержано в памяти** | — | Это единственный прямой сигнал обучения |

**Вывод.** Активность за компьютером даёт только **косвенные** сигналы: «в плане или нет», «сколько переключений», «долго ли простой». Об обучении говорят только результаты вопросов и задач. Постоянная запись экрана **не нужна** ни для одной функции MVP.

## 4. Варианты стека

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Tauri 2 + React + TypeScript + Rust** | Маленький бинарник, ядро на Rust (системная интеграция, FSRS через `fsrs-rs`), меньше памяти, чем у Electron в обычных условиях | На Linux рендерит WebKitGTK: медленнее Chromium, известны проблемы на Wayland + NVIDIA (пустое окно, `Error 71`; обход — `WEBKIT_DISABLE_DMABUF_RENDERER=1`), AppImage может принудительно включать X11 ([Tauri docs](https://v2.tauri.app/develop/debug/linux-graphics/)) |
| Electron + TypeScript | Одинаковый Chromium везде, зрелая экосистема | 150–500 МБ памяти, системная интеграция через Node-модули |
| Qt 6 / QML + C++ | Нативно на Linux, хорошо работает на Wayland, в стиле Omarchy-приложений | Медленнее разработка интерфейса, нужен C++ |
| Чистый Rust GUI (egui, iced, Slint) | Один язык, мало памяти | Сложные интерфейсы (редактор, графики) писать дольше |
| Локальный веб-сервер + браузер | Самый простой прототип | Нет трея, нет глобальных горячих клавиш, слабая системная интеграция |

Сравнения памяти Tauri и Electron в блогах противоречат друг другу (от «в 2–10 раз меньше» до «на реальной нагрузке разница сокращается»). [GitHub issue](https://github.com/tauri-apps/tauri/issues/5889). Нужно мерить на своём приложении.

**Рекомендация: Tauri 2**, но с двумя оговорками:
1. **Всё ядро — в отдельном Rust-крейте** (`whiteroom-core`: база данных, FSRS, модель знаний, планировщик, адаптеры активности) без зависимости от Tauri. Если WebKitGTK окажется проблемой, интерфейс можно заменить (Electron, Qt), не трогая логику.
2. **Первый шаг разработки — прототип на 1–2 дня**: окно Tauri на Hyprland с подпиской на `socket2`, проверка на NVIDIA и на Intel/AMD.

## 5. Хранение

- **SQLite** (через `rusqlite` или `sqlx`), один файл в `~/.local/share/whiteroom/`. WAL-режим. Миграции схемы с первого дня.
- Журнал событий активности — отдельная таблица с автоочисткой (по умолчанию хранить 30 дней, агрегаты — бессрочно).
- Шифрование базы (SQLCipher) — опция позже. На уровне MVP достаточно прав `0600` и полного шифрования диска, которое уже стоит у большинства пользователей.
- Экспорт всех данных в JSON и CSV + импорт и экспорт Anki `.apkg`.

## 6. ИИ: облако и локальная модель

| Задача | Требования | Где выполнять |
|---|---|---|
| Генерация вопросов по материалу | Качество важнее скорости | Облачная модель (Claude API или другой провайдер), по согласию |
| Проверка объяснений, подсказки по уровням | Качество, рассуждения | Облако; локально — упрощённый вариант |
| Классификация «окно относится к теме?» | Быстро, приватно, много раз | **Локально**: сначала правила и списки, потом маленькая модель |
| Планирование сессии | Детерминированно | **Не LLM**: алгоритм в ядре (см. `cognitive-engine.md`) |

- Локальный запуск: llama.cpp или Ollama (HTTP API на localhost). Модель на 3–8 млрд параметров в 4-битной квантизации занимает несколько ГБ памяти и работает на CPU медленно, но приемлемо для фоновой классификации. **[инженерная оценка]**, нужно мерить.
- Провайдер ИИ — за интерфейсом `LlmProvider`. Ключ API хранить в системном хранилище секретов (Secret Service / `libsecret`), а не в базе.
- **Что уходит в облако.** Только материал, который пользователь сам дал для генерации вопросов, и его ответы. **Никогда** — журнал окон, заголовки, URL. Перед первой отправкой показывать, что именно уйдёт.
- **Офлайн.** Повторения, задачи, расписание, блокировка и статистика работают без сети. Без сети не работают только генерация новых вопросов и проверка свободных ответов через облако; они ставятся в очередь.

## 8. Безопасность и разрешения

- Каждый источник данных включается отдельно (окна, браузер, IDE, скриншоты), по умолчанию всё **выключено**. Экран «что WHITE ROOM видит сейчас» в один клик.
- В Tauri — минимальный набор capabilities: интерфейс не получает прямого доступа к файловой системе и shell, только к командам ядра.
- Код, который сгенерировал ИИ или вставил пользователь, запускается только по контракту из 8.1. Если песочница недоступна, код не запускается.
- Никакого root в MVP. Привилегированные функции (hosts) — отдельный маленький помощник через polkit, позже.
- Никакой телеметрии по умолчанию.

### 8.1 Контракт песочницы для кода

Отвечает на замечание C2 из [независимого ревью](independent-review.md#c2-running-learner-or-generated-code-creates-a-security-boundary-with-no-defined-contract). Прототип проверен на машине разработчика 19.11.2026 (Arch, bubblewrap 0.13.1, systemd 262), см. «Приёмочные тесты».

**Что защищаем.** Систему и данные пользователя от кода, который написал ИИ, скопировал пользователь или принесли зависимости задачи. **Не защищаем** честность оценки: учащийся и есть пользователь, обмануть тесты он может только себя. Поэтому вердикт можно получать из того же процесса, что и решение. Тесты и рубрики лежат отдельно от решения и монтируются только для чтения.

**Модель угроз.** Код может: читать файлы, ходить в сеть, плодить процессы, съедать память и диск, оставлять фоновые процессы, использовать унаследованные дескрипторы и сокеты рабочего стола (Wayland, D-Bus, Hyprland IPC, сокет WHITE ROOM). От уязвимостей ядра контракт **не** защищает (user namespaces расширяют поверхность атаки) — это остаточный риск, о нём сказано в настройках.

**Правила.**

| # | Правило | Как обеспечивается |
|---|---|---|
| R1 | Запуск только по явному действию пользователя («Запустить тесты»), никогда автоматически при генерации | Ядро |
| R2 | Нет сети | `bwrap --unshare-all` (свой network namespace, только `lo`) |
| R3 | Минимальная ФС: `/usr` только чтение, `/proc` и `/dev` свои, `/tmp` — tmpfs 64 МБ. Нет `$HOME`, `/run/user`, `/etc` (кроме `ld.so.cache`) | `--ro-bind /usr`, `--proc`, `--dev`, `--size … --tmpfs /tmp` |
| R4 | Каждый запуск — новая папка задания в tmpfs (`$XDG_RUNTIME_DIR`): `src/` только для чтения, `out/` на запись (бинарь после gcc). На диск хоста писать нельзя: запись в tmpfs засчитывается в `MemoryMax` | `--ro-bind <job>/src /work/src`, `--bind <job>/out /work/out` |
| R5 | Пустое окружение: `PATH`, `HOME=/work`, `LANG`. Никаких токенов, `DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_*`, `SSH_AUTH_SOCK` | `env -i` |
| R6 | Наследуются только fd 0/1/2: stdin = `/dev/null`, stdout и stderr — каналы (pipes) ядра | Перед `exec` — `close_range(3, ~0)`, в Rust через `pre_exec` или проверка, что все fd ядра открыты с `O_CLOEXEC` |
| R7 | Лимиты на **всё дерево процессов**: память 256 МБ без swap, 64 процесса, 1 ядро CPU, 10 с на запуск (настраивается задачей, потолок 60 с) | cgroup через `systemd-run --user --scope -p MemoryMax=256M -p MemorySwapMax=0 -p TasksMax=64 -p CPUQuota=100% -p RuntimeMaxSec=10` |
| R8 | После завершения не остаётся процессов и файлов | Остановка scope убивает весь cgroup, `--die-with-parent`; временная папка удаляется ядром |
| R9 | Вывод ограничен: ядро читает максимум 1 МБ stdout/stderr, остальное отбрасывает | Ядро |
| R10 | Без привилегий: `--cap-drop ALL`, `--new-session` (нельзя писать в терминал через `TIOCSTI`) | `bwrap` |
| R11 | Нет обходного пути: если `bwrap`, user namespaces или делегирование cgroup недоступны, запуск **выключен** с объяснением. Обычный подпроцесс вместо песочницы — никогда | Проверка при старте и перед каждым запуском |

**Команда (эталон для реализации).**
```
systemd-run --user --scope --quiet --collect \
  -p MemoryMax=256M -p MemorySwapMax=0 -p TasksMax=64 -p CPUQuota=100% -p RuntimeMaxSec=10 \
  -- env -i PATH=/usr/bin HOME=/work LANG=C.UTF-8 \
  bwrap --unshare-all --die-with-parent --new-session --cap-drop ALL \
    --ro-bind /usr /usr --symlink usr/bin /bin --symlink usr/lib /lib --symlink usr/lib /lib64 \
    --ro-bind /etc/ld.so.cache /etc/ld.so.cache \
    --proc /proc --dev /dev --size 67108864 --tmpfs /tmp \
    --ro-bind "$JOB/src" /work/src --chdir /work \
    <интерпретатор> <тест-раннер>
```
Ядро запускает это с закрытыми fd ≥ 3 (R6).

**Упаковка.** AUR — да: `bubblewrap` и `systemd` в зависимостях. AppImage — да, если `bwrap` есть в системе (свой setuid-`bwrap` не поставляем). Flatpak — запуск кода выключен: вложенный `bwrap` там не работает.

**Приёмочные тесты.** Без них запуск не включается. Прогонять в CI и при старте на машине пользователя (короткая версия):

| Тест | Ожидание | Результат прототипа |
|---|---|---|
| `os.listdir("/home")`, чтение `~/.ssh/*` | ошибка | ✅ `FileNotFoundError` |
| `os.listdir("/run/user")` (Wayland, D-Bus) | ошибка | ✅ |
| TCP к `1.1.1.1:53` | ошибка | ✅ `OSError` |
| Запись в `/work/src`, `/usr` | ошибка | ✅ |
| Переменные окружения | только `PATH`, `HOME`, `LANG`, `PWD` | ✅ |
| Унаследованный fd 7 на файл хоста | недоступен | ❌ без R6 прочитался; ✅ с закрытием fd (`Bad file descriptor`) |
| 200 фоновых процессов | упор в `TasksMax` | ✅ `fork: Resource temporarily unavailable` |
| Выделение 600 МБ | убит OOM, код 137 | ✅ |
| `setsid sleep 100 &` + `sleep 100` | убито всё дерево через 10 с, ничего не осталось | ✅ |

Главный урок прототипа: **`bwrap` сам не закрывает унаследованные дескрипторы**, поэтому R6 — обязанность ядра. Тест на fd должен быть в CI.

**Реализация (19.11.2026):** `whiteroom-core/src/sandbox.rs`, приёмочные тесты — `whiteroom-core/tests/sandbox.rs` (7 тестов, включая компиляцию C через gcc внутри песочницы и запись 400 МБ, упирающуюся в лимит). Тест на fd проверен мутацией: без `close_range` он падает.

## 9. Ресурсы

Целевые значения для MVP (проверить на прототипе):
- Фоновый процесс без открытого окна: < 50 МБ RAM, ~0% CPU (события, а не опрос).
- Окно открыто: < 300 МБ.
- Локальная LLM — отдельный процесс, загружается по запросу и выгружается.
- Аккумулятор: никакого опроса раз в секунду; Hyprland и X11 присылают события сами.

## 10. Открытые технические вопросы

1. Как WebKitGTK ведёт себя на машине разработчика (Hyprland, видеокарта)? Нужен прототип.
2. Поддерживать ли Flatpak? В песочнице Flatpak доступ к сокету Hyprland и `/proc` ограничен. Предлагаю на старте: пакет AUR и AppImage.
3. Firefox или Chromium как первый браузер? У Firefox блокирующий `webRequest` проще, у Chromium больше пользователей.
4. Какой локальной модели хватает для классификации «по теме / не по теме»? Возможно, хватит правил и эмбеддингов без генеративной модели.
